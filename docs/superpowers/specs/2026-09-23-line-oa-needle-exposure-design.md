# สเปก LINE OA เข็มทิ่มตำ

วันที่: 23 กันยายน 2569  
สถานะ: ตรวจทานแล้วและแตกเป็น tickets วันที่ 25 กันยายน 2569; รอทบทวนแผนก่อนเริ่ม implementation

## เป้าหมายและขอบเขต

สร้าง LINE Official Account สำหรับตอบคำถามเรื่องการสัมผัสเลือดหรือสารคัดหลั่งขณะปฏิบัติงาน ผู้ใช้ทั่วไปเพิ่มเพื่อนและถามได้ คำตอบทางการแพทย์มาจากข้อความที่ผู้พัฒนานำจากแนวทางลงในคลังข้อมูลที่กำหนดไว้ล่วงหน้าเท่านั้น ระบบไม่วินิจฉัย ไม่ประเมินความเสี่ยงเฉพาะบุคคล และไม่สร้างคำตอบทางคลินิกใหม่

โครงการนี้เป็นระบบใหม่ แยกจาก `medical-line-bot` เดิมและระบบคลินิกอื่น Repo เดิมใช้ศึกษาแนวคิด JSON และ rule-based เท่านั้น ไม่คัดลอกข้อมูลยา โครงสร้างบทสนทนา หรือสถานะผู้ใช้มาใช้โดยปริยาย

ความสำเร็จของ MVP คือผู้ใช้กดเมนูหรือพิมพ์คำถามที่ตรงกับ alias ที่รองรับแล้วได้รับคำตอบตรง route ที่กำหนด เลือกอ่านกรณีย่อยต่อได้ เปิดแบบฟอร์มรายงานความเสี่ยงได้ และคำถามนอกขอบเขตได้รับข้อความปฏิเสธที่กำหนดไว้

## แหล่งข้อมูลและหลักการเขียนคำตอบ

1. แหล่งอ้างอิงหลักคือ `แนวทางเมื่อบุคลากรทางการแพทย์สัมผัสเลือ.pdf` ฉบับปรับปรุงครั้งที่ 3 วันที่ 3 กันยายน 2569
2. `แนวทางเมื่อบุคลากรทางการแพทย์สัมผัสเลือ.docx` ใช้ตรวจและถอดข้อความ ส่วน `แนวทางเมื่อบุคคลทางการแพทย์.jpg` และภาพตัวอย่าง LINE ใช้ตรวจลำดับทางเลือกและรูปลักษณ์
3. หาก PDF, DOCX และภาพไม่ตรงกัน ให้ยึด PDF ถ้าข้อความใน PDF เองกำกวม ให้ปิดเฉพาะ route ที่ได้รับผลกระทบจนกว่าจะมีข้อความยืนยัน ผู้พัฒนาไม่แก้ความหมายทางคลินิกเอง
4. คลังคำตอบทางการแพทย์บันทึกเป็น JSON ที่ผ่าน schema validation แต่ละข้อความมี `routeId`, หมวด, เนื้อหา, หน้าอ้างอิงใน PDF, เวอร์ชันเอกสาร และปุ่มทางถัดไป แยกไฟล์ข้อมูลแนวทาง, alias, metadata และข้อความติดต่อ การแสดงผล Flex และข้อความปกติอ่านจากข้อความชุดเดียวกัน
5. ข้อความ UX เช่น คำทักทาย คำแนะนำการใช้เมนู และคำตอบไม่พบข้อมูล แยกจากข้อความทางการแพทย์อย่างชัดเจน
6. ไม่มีปุ่มเปิดหรือดาวน์โหลด PDF ฉบับเต็มใน LINE OA ผู้ใช้เข้าถึงคำตอบของบอตได้ทุกคนตาม route ที่เปิดใช้งาน
7. การแสดงชื่อเอกสารท้ายทุกคำตอบยังไม่รวมใน MVP ตามการตัดสินใจรอบ grill แต่ข้อมูลเวอร์ชันและตำแหน่งอ้างอิงอยู่ใน JSON และในชุดทดสอบ

### คำตอบและการนำทาง

- ข้อความเกริ่นสั้นใช้ bubble ปกติ ขั้นตอนที่มีลำดับใช้ Flex Message และทางเลือกถัดไปใช้ Quick Reply
- คำตอบยาวแบ่งตาม branch เพื่อให้ผู้ใช้เห็นเฉพาะกรณีที่เลือก ไม่ส่งทุกเส้นทางในข้อความเดียว
- ปุ่มทุกปุ่มส่ง `routeId` ที่กำหนดไว้ผ่าน postback ไม่ใช้ข้อความที่แสดงบนปุ่มเป็นตัวตัดสิน route
- คำถามที่พิมพ์ใช้ alias ที่กำหนดไว้ล่วงหน้า ปรับช่องว่าง ตัวพิมพ์อังกฤษ คำลงท้ายสุภาพ 1 ชุด และเครื่องหมายท้ายข้อความที่กำหนดเท่านั้น ไม่เดา route ทางคลินิกจากคำใกล้เคียง ไม่ใช้ LLM, embeddings หรือการค้นหาเชิงความหมาย
- การพิมพ์คำถามไม่ใช่การถามภาษาธรรมชาติแบบครอบจักรวาล: ถ้อยคำที่ยังไม่ได้เพิ่มเป็น alias อาจเข้า fallback แม้ผู้ใช้เห็นว่าเป็นเรื่องเดียวกัน
- หากข้อความเข้าได้หลาย route หรือไม่มี route ที่มั่นใจ ให้ถามให้เลือกกรณี หรือกลับไปเลือกจากเมนู ไม่เดาคำตอบ
- คำถามเรื่องอาการหรือการรักษาเฉพาะบุคคล รูปภาพ ไฟล์ เสียง และข้อความนอกขอบเขตได้รับคำตอบมาตรฐานที่ไม่ให้คำแนะนำทางคลินิกใหม่
- รองรับเฉพาะแชทส่วนตัว 1:1; ไม่ตอบในกลุ่มหรือห้องหลายคน

ข้อปรับปรุงที่ผู้ใช้อนุมัติ 16 ต.ค. 2569: รับคำทักทาย/ขอบคุณจาก alias แบบตรง
และใช้คำทักทายสั้นสองบรรทัดตามที่เลือก ไม่ใส่คำเกริ่นซ้ำหน้าคำตอบคลินิก
เมื่อข้อความไม่ตรง alias อาจเสนอชื่อหัวข้อเมนูภาษาไทยตามรายการใน `ui.json`
ที่ต่างไม่เกิน 1 ตัวอักษรและตรงเพียงหัวข้อเดียว ต้องให้ผู้ใช้กด postback ยืนยัน
ก่อนแสดงคำตอบ ข้อยกเว้นนี้ใช้เฉพาะการเสนอหัวข้อ ไม่ใช้ fuzzy routing กับข้อมูลคลินิก
ผลบวก/ลบ เวลา ชื่อยา ขนาดยา รหัส และตัวเลขไม่อยู่ในรายการเสนอคำใกล้เคียง
ข้อความยาว ประโยคที่ไม่ตรงคำที่กำหนด หรือกรณีไม่ชัดให้แสดงเมนู ไม่เดาข้อมูล
คำทักทาย/ขอบคุณ ข้อความที่ไม่ตรง และคำถามยืนยัน ไม่ล้างหรือยืดอายุบริบทเดิม
ปุ่มกลับเมนู/เริ่มใหม่ยังล้างบริบทตามเดิม เนื้อหาและสถานะใน `routes.json` ไม่เปลี่ยน

ผู้ใช้อนุมัติให้เพิ่มความครอบคลุมของคำพิมพ์ในวันเดียวกัน: ใช้ตัวปรับข้อความร่วมกัน
ก่อนเทียบ alias ทั้งข้อความ รองรับคำลงท้าย เช่น ครับ/ค่ะ/คะ/คับ/นะครับ/ครับผม
และเครื่องหมายท้าย `? ! . 。 … ！ ？` ไม่ลบคำปฏิเสธ ตัวเลข +/- หรือเครื่องหมายกลางประโยค
เพิ่มสำนวนใน aliases.json/ui.json แบบกำหนดปลายทางชัดเจน คำผลตรวจ/เวลาแบบยาวหรืออังกฤษ
ยังต้องอยู่ในบริบทเดิมที่ถูกต้อง ข้อความที่มีหลายเงื่อนไข ไม่แน่ใจ หรือข้อมูลผู้ป่วย
ไม่ถูกตัดเหลือ keyword เพื่อเลือกกรณีให้ Postback ยังคงเทียบ ID ตรงทุกตัวอักษร

## ต้นไม้ของ route cases

ต้นไม้ข้อมูลหลักต้องครอบคลุมเนื้อหาทั้งฉบับตาม PDF และแบ่งอย่างน้อยดังนี้:

1. การปฐมพยาบาล: ของมีคม/ผิวหนังที่ไม่ปกติ, กระเด็นเข้าตา, กระเด็นเข้าปาก
2. การแจ้งหัวหน้าเวร การซักประวัติและบันทึกหลักฐาน รวมถึงหมายเหตุกรณี OPD
3. การเจาะเลือดผู้ป่วยตามรหัส IC04 และผลตรวจทุกตัวเป็นลบหรือมีผลบวกอย่างน้อยหนึ่งตัว
4. ทางผลลบ: ขั้นตอนรายงานต่อ IC และ HRMS ตามแนวทาง
5. ทางผลบวก: ในเวลาราชการหรือนอกเวลาราชการ, จุดพบแพทย์/ICN, การเจาะเลือดบุคลากรภายในกรอบเวลาที่เอกสารระบุ, รหัส IC05 หรือ IC06, oPEP และการติดตาม
6. หมายเหตุเพิ่มเติมในเอกสาร: สูตรยา, การติดตาม HIV/HCV, HBIG/วัคซีน Hepatitis B และเงื่อนไขค่า Cr แยกเป็น route ย่อยที่ผู้ใช้เลือกอ่านได้
7. ความรู้ภาพรวม: ข้อความที่ประกอบจากส่วนที่ตรวจได้ใน PDF และปุ่มไปยัง route รายละเอียด โดยไม่เพิ่มข้อสรุปทางคลินิกใหม่

แต่ละ route มีข้อความทางการแพทย์ที่ตรึงไว้ใน JSON หากต้นฉบับมีข้อความขัดกันหรืออ่านได้สองความหมาย route นั้นต้องไม่ผ่านการเปิดใช้งานจนกว่าจะได้รับข้อความที่ยืนยันแล้ว

## สถาปัตยกรรมและข้อมูลไหล

ใช้ Cloudflare Workers Free พร้อม TypeScript เป็น webhook server เดียว ไม่มีฐานข้อมูลสำหรับเนื้อหา (JSON อยู่ใน deployment); Workers KV ใช้เฉพาะสถานะชั่วคราว ไม่ใช้ R2, LIFF, ระบบหลังบ้าน หรือบริการ AI

```text
ผู้ใช้ LINE 1:1
    → LINE Platform
    → HTTPS POST /webhook บน Cloudflare Worker
    → ตรวจ x-line-signature จาก raw body
    → ตรวจชนิด event และ routeId / alias
    → อ่าน JSON คำตอบที่รวมอยู่ใน deployment
    → อ่าน/เขียน Workers KV เฉพาะ context และ event deduplication
    → LINE Reply API
    → ผู้ใช้ LINE

Rich Menu “รายงานอุบัติการณ์”
    → postback → คำเตือน + ปุ่ม URI → Google Form
```

Worker มีหน่วยย่อยที่แยกหน้าที่ชัดเจน: transport สำหรับ LINE, ตัวตรวจ signature, deterministic router, content loader/validator, response renderer และ context store การตั้ง Rich Menu เป็นงานตั้งค่าผ่าน LINE API ระหว่าง deploy ไม่ใช่การเรียก API สร้างเมนูทุกครั้งที่มีข้อความ

`LINE_CHANNEL_SECRET`, `LINE_CHANNEL_ACCESS_TOKEN` และ secret สำหรับทำ HMAC เก็บใน Cloudflare secrets ไม่อยู่ใน Git หรือ JSON เนื้อหา มี Worker และ LINE OA ชุดเดียวตามข้อจำกัดด้านเวลา การเปลี่ยนแปลงต้องผ่านการทดสอบก่อน deploy และใช้ประวัติ deployment เพื่อย้อนกลับ

## สถานะและการเก็บข้อมูล

Workers KV เก็บเฉพาะ:

- `context:<HMAC(LINE user ID)>` → `lastRouteId`, หมดอายุ 30 นาที; เริ่มหัวข้อใหม่แล้วแทนค่าเดิม หรือเมื่อตั้งใจเริ่มใหม่ให้ล้างบริบท
- `event:<hash(webhookEventId)>` → สถานะว่าตอบสำเร็จแล้ว, หมดอายุ 24 ชั่วโมง เพื่อช่วยลดการตอบซ้ำจาก webhook redelivery; ไม่ทำเครื่องหมายว่าสำเร็จก่อน LINE Reply API ตอบรับ

ไม่เก็บข้อความผู้ใช้ ข้อความคำตอบ ชื่อ HN หรือประวัติการสนทนาในระบบของบอต และไม่บันทึก raw webhook ลง application logs ประวัติในแอป LINE หรือ Google Form อยู่ภายใต้นโยบายของบริการเหล่านั้น ไม่ใช่ข้อมูลที่ Worker จัดเก็บ

KV เป็นระบบที่เผยแพร่ข้อมูลแบบ eventual consistency การตรวจ event ซ้ำจึงเป็น best effort ไม่ใช่การรับประกัน exactly once; LINE reply token ใช้ได้ครั้งเดียวและตัวตอบต้องจัดการข้อผิดพลาดจาก Reply API อย่างปลอดภัย หาก KV เกินโควตาหรือขัดข้อง route ที่ไม่ต้องใช้บริบทควรยังตอบได้ โดยปิดการถามต่อที่ต้องอาศัย `lastRouteId` ชั่วคราว

ข้อชี้แจงจาก implementation (9 ต.ค. 2569): เก็บ `expiresAt` และตรวจเมื่ออ่านเพื่อไม่ใช้บริบทหมดอายุ การเปลี่ยน/ล้างหัวข้อและการกันซ้ำข้าม requests ยังเป็น best effort: KV อาจคืนหัวข้อเก่าที่ยังไม่หมดอายุระหว่าง replication และ event ที่เข้าพร้อมกันอาจผ่านการตรวจพร้อมกันได้ หากเขียนหัวข้อใหม่ล้มเหลวให้พยายามลบหัวข้อเดิม แต่ไม่รับประกันการลบค่าค้างทันที การรับประกัน latest-context หรือ exactly-once ต้องใช้ state store แบบ strong consistency แทน KV

## ความผิดพลาดและการตอบกลับ

- signature ผิด: ตอบ HTTP 401 โดยไม่ประมวลผล event
- event จาก group/room หรือชนิดที่ไม่รองรับ: ตอบ HTTP 2xx โดยไม่ส่งข้อความ; postback ในแชท 1:1 ต้องเข้าสู่ router ตามปกติ
  ข้อชี้แจง Ticket 6 (11 ต.ค. 2569): ข้าม event ที่ไม่รู้จัก/ไม่มี replyToken ตามเดิม;
  สำหรับ message รูป/ไฟล์/เสียงใน 1:1 ที่ตอบได้ ให้ส่ง ui.unsupported และเมนู
  ตามข้อกำหนดคำถามด้านบน โดยไม่อ่านไฟล์หรือสร้างคำแนะนำทางคลินิก
- route ไม่ตรงหรือกำกวม: ตอบ fallback ที่กำหนดไว้ พร้อมทางกลับเมนู
- JSON หรือ schema ไม่ผ่าน: หยุด build/deploy; runtime ไม่ควรเผยแพร่ชุดข้อมูลไม่สมบูรณ์
- LINE Reply API ล้มเหลว: บันทึกเฉพาะรหัสข้อผิดพลาดและ routeId ที่ไม่ระบุตัวบุคคล แล้วให้ webhook คืนสถานะล้มเหลวโดยไม่บันทึก raw body; การส่งซ้ำจะเกิดได้ก็ต่อเมื่อเปิด webhook redelivery และไม่รับประกันว่าผู้ใช้จะได้รับคำตอบ เพราะ reply token อาจใช้ไปแล้วหรือหมดอายุ
- Google Form เปิดไม่ได้: ข้อความตอบมี URL ที่คัดลอกได้เป็นทางสำรอง; Worker ไม่รับและไม่เก็บข้อมูลในฟอร์ม และไม่รับประกันความพร้อมใช้งานของบริการ Google

## การทดสอบและเปิดใช้

1. ตรวจ schema ของ JSON รวมถึง `routeId` ไม่ซ้ำ, `nextRouteId` ที่มีอยู่จริง, ข้อความไม่ว่าง และข้อมูลอ้างอิง PDF ครบ
2. Route tests ตรวจเมนู postback, alias ภาษาไทย, การถามต่อโดยใช้ `lastRouteId`, อายุ 30 นาที, เปลี่ยนเมนูแล้วเปลี่ยนบริบท, route กำกวม และ fallback
3. Content snapshots ตรวจข้อความทางการแพทย์ที่ถอดและตรึงไว้ทุกตัวอักษรและรูปแบบ renderer ที่ไม่เปลี่ยนความหมาย โดยผู้พัฒนาเทียบ source mapping กับ PDF ก่อนยอมรับ snapshot ใหม่; การทดสอบนี้ยืนยันความตรงกับต้นฉบับ ไม่ใช่การรับรองความถูกต้องทางคลินิกของต้นฉบับ
4. Webhook tests ตรวจ signature บน raw body, event ซ้ำ, 1:1 เท่านั้น, LINE Reply API error, KV อ่าน/เขียนไม่ได้, การตอบแบบไม่จำบริบทเมื่อ KV ล้มเหลว และไม่มี raw message ใน log
5. ทดสอบบน LINE OA จริงด้วยบัญชีของผู้พัฒนาบนโทรศัพท์ก่อนแชร์ QR: ทุกช่อง Rich Menu, การพิมพ์คำถาม, การถามต่อ, ปุ่มฟอร์ม, ข้อความนอกขอบเขต และกรณีตอบไม่ได้; LINE บนคอมพิวเตอร์ไม่แสดง Rich Menu
6. หลังการทดสอบจริงผ่าน จึงแชร์ QR ให้กลุ่มผู้ใช้เล็กทดลอง ไม่มีระบบ staging แยก

## ข้อจำกัดของ MVP

- ไม่ผูก LINE user กับรหัสบุคลากร เพราะผู้ใช้ทั่วไปเข้าได้
- ไม่มีระบบวินิจฉัยหรือข้อเสนอการรักษาที่สร้างตามข้อมูลของผู้ถาม
- ไม่มีหน้าจอแก้เนื้อหา; ผู้พัฒนาแก้ JSON, ตรวจ source mapping และ tests แล้ว deploy
- ไม่มีประวัติแชทหรือ analytics ระดับผู้ใช้
- ไม่มีเอกสาร PDF ฉบับเต็มให้เปิดในแชท
- ช่องติดต่อผู้เกี่ยวข้องใช้ข้อมูลที่ผู้ใช้ให้วันที่ 20 ต.ค. 2569 แล้ว ยังไม่ยืนยันว่าวิธีโทรเป็นภายใน จึงแสดงเฉพาะชื่อหน่วยงาน/หมายเลข ไม่ติดป้ายเบอร์ภายในหรือปุ่มโทร
- ยังไม่กำหนดบรรทัดแสดงชื่อเอกสารและเวอร์ชันในทุกคำตอบ แต่เก็บ metadata เพื่อเพิ่มได้ภายหลัง
- ก่อนเผยแพร่แก่บุคคลทั่วไป ผู้ว่าจ้างต้องยืนยันว่ามีสิทธิ์เผยแพร่ข้อความที่นำมาจากแนวทาง แม้บอตจะไม่เปิด PDF ฉบับเต็ม

## ความเป็นไปได้ ระยะเวลา และต้นทุนโดยประมาณ

ฟังก์ชันตามสเปกทำได้โดยไม่ใช้ AI หรือเซิร์ฟเวอร์แบบเสียรายเดือน แต่คำว่า “ฟรี” หมายถึงค่าบริการแพลตฟอร์มในระยะ pilot ภายใต้โควตา ไม่รวมเวลาพัฒนา โดเมนที่ซื้อเพิ่ม งานออกแบบที่จ้างเพิ่ม หรือบริการส่งข้อความแบบ push/broadcast สมมติว่ามีผู้ใช้งานจริงรวมประมาณ 10 คน, ใช้ไม่เกิน 20 การโต้ตอบต่อคนต่อวัน, ใช้ LINE OA แผนฟรี, ใช้เฉพาะ Reply API และใช้ URL `workers.dev` จะคาดได้ว่าค่าบริการรายเดือนเป็น 0 บาท แต่ต้องวัดการใช้งานจริงหลังเปิดใช้

### วิเคราะห์จุดชนลิมิตของ Free tier (ตรวจข้อมูล 25 กันยายน 2569)

โควตาด้านล่างเป็นของบัญชี Cloudflare ไม่ใช่โควตาที่สงวนให้บอตนี้โดยเฉพาะ หากมี Worker หรือ KV อื่นในบัญชีเดียวกัน ต้องหักการใช้งานเหล่านั้นก่อน ค่ารายวันรีเซ็ตเวลา 00:00 UTC หรือ 07:00 น. ตามเวลาไทย

| ทรัพยากร | เพดาน Free | เมื่อชนลิมิต บอตนี้เป็นอย่างไร |
| --- | --- | --- |
| Worker requests | 100,000 requests/วัน | คำขอถัดไปถูก Cloudflare ปฏิเสธด้วย Error 1027; webhook เข้า Worker ไม่ได้ จึง **ไม่ตอบ** จนกว่าโควตาจะรีเซ็ต |
| Worker CPU | 10 ms ต่อ HTTP request | หากการประมวลผลคำขอหนึ่งเกินเพดานอย่างต่อเนื่อง Worker อาจถูกยุติด้วย Error 1102 และ **ไม่ตอบคำขอนั้น** แม้จำนวนผู้ใช้ยังน้อย; ต้องวัด CPU จริงตอนทดสอบ |
| KV reads | 100,000 reads/วัน | การอ่านบริบท/สถานะกันซ้ำล้มเหลว; ต้องให้ route จากเมนูหรือ alias ที่ไม่ต้องใช้บริบทยัง **ตอบได้** ส่วนคำถามต่อที่ต้องใช้บริบทให้ตอบข้อความขอให้เลือกหัวข้อใหม่ |
| KV writes | 1,000 writes/วัน | การบันทึกบริบท/สถานะกันซ้ำล้มเหลว; ต้องไม่ปล่อยให้ error นี้ขัดการตอบ route ที่ทราบแล้ว แต่การจำหัวข้อล่าสุดและกันตอบซ้ำอาจใช้ไม่ได้ชั่วคราว |
| KV deletes / พื้นที่ | 1,000 deletes/วัน / 1 GB | การลบที่เกินโควตาล้มเหลว หรือบันทึกข้อมูลเพิ่มไม่ได้เมื่อพื้นที่เต็ม; ค่า TTL ยังเป็นกลไกหลักในการหมดอายุข้อมูลชั่วคราว |
| KV เขียน key เดิมถี่เกิน | 1 write/วินาทีต่อ key | ผู้ใช้กดหลายปุ่มติดกันเร็วมากอาจทำให้การเขียน `context` ล้มเหลวก่อนชนโควตารายวัน; ให้ตอบ route ปัจจุบันต่อได้และไม่อ้างบริบทที่บันทึกไม่สำเร็จ |

การคิดแบบคร่าว ๆ สำหรับสเปกนี้: 1 การโต้ตอบที่ตอบสำเร็จใช้ประมาณ 1 Worker request และ KV 2 writes (1 ครั้งสำหรับ `context`, 1 ครั้งสำหรับ `event` กันซ้ำ) ดังนั้น **KV writes เป็นคอขวดก่อน Worker requests** หากไม่มีการใช้งานอื่น `1,000 ÷ 2 ≈ 500 การโต้ตอบ/วัน` คือจุดที่เริ่มเขียน KV ไม่ได้ ไม่ใช่จุดที่บอตหยุดตอบทั้งหมด ตัวเลขจริงอาจต่ำหรือสูงกว่านี้ตามชนิด event, การเขียนที่ไม่จำเป็น, คำขอทดสอบ และการใช้งานร่วมบัญชี

ตัวอย่างสมมติ: 10 คน × 20 การโต้ตอบ/วัน = ประมาณ 200 การโต้ตอบ, 200 Worker requests และ 400 KV writes/วัน (40% ของโควตา writes) ให้ใช้ **300 การโต้ตอบ/วัน หรือราว 600 KV writes/วัน** เป็นระดับวางแผนที่ยังมีส่วนเผื่อ และเริ่มตรวจสาเหตุเมื่อ KV writes แตะ 700/วัน ไม่รอให้ชน 1,000/วัน บอตเปิดให้บุคคลทั่วไปใช้ได้ ดังนั้น “10 คน” เป็นเพียงประมาณการ ไม่ใช่ขีดจำกัดผู้ใช้

LINE Messaging API ไม่นับข้อความที่ส่งด้วย Reply API ในโควตาข้อความรายเดือน แต่ถ้าเปลี่ยนไปใช้ push/broadcast ต้องคำนวณโควตา LINE OA ใหม่ การใช้ Free tier เกินเพดานไม่ใช่การรับประกันว่าจะตอบต่อได้: Workers ถูกปฏิเสธและ KV operation ล้มเหลวตามกรณีข้างต้น โดยไม่อัปเกรดเป็นแผนเสียเงินอัตโนมัติ

หลังแตกงานเป็น tickets ประเมินสำหรับผู้พัฒนาคนเดียวที่มีบัญชีและสิทธิ์ตั้งค่า LINE OA/Cloudflare พร้อมแล้ว: ประมาณ 8–12 วันทำงาน (ราว 50–80 ชั่วโมง) โดยส่วนที่ใช้เวลามากสุดคือถอดและตรวจเนื้อหา/route 2–3 วัน ตัวเลขนี้ละเอียดกว่าประมาณการเบื้องต้น 7–10 วันก่อนแตกงาน หากยังต้องเปิดบัญชี ขอสิทธิ์ ตรวจถ้อยคำที่กำกวมในเอกสาร หรือแก้ภาพเมนูหลายรอบ ให้เผื่อเพิ่มอีก 3–5 วันทำงาน

`workers.dev` ใช้เริ่มได้โดยไม่ซื้อโดเมน แต่ Cloudflare ระบุว่าเหมาะกับงานทดลอง/งานอดิเรกมากกว่าบริการสำคัญ การใช้งานจริงที่ต้องการความน่าเชื่อถือสูงควรประเมินโดเมนของผู้ว่าจ้างภายหลัง ค่าใช้จ่ายอาจไม่เป็นศูนย์ในระยะนั้น

## เกณฑ์ยอมรับงาน

- ทุกคำตอบทางการแพทย์ที่เปิดใช้มี route และตำแหน่งอ้างอิงใน PDF ตรวจย้อนกลับได้
- ไม่มี branch ใดสร้างข้อความทางคลินิกด้วย AI หรือการเดาจากคำถาม
- ผู้ใช้กดเมนูทั้ง 6 ช่องและพิมพ์คำถามที่รองรับได้บน LINE OA จริง
- คำถามต่ออ้างถึง route ล่าสุดภายใน 30 นาที และไม่อ้าง route เก่าหลังหมดอายุหรือเปลี่ยนเมนู
- การรายงานความเสี่ยงพาไป Google Form หลังผู้ใช้เห็นคำเตือน
- ระบบไม่เก็บข้อความแชทใน KV หรือ application logs
- tests ทั้ง schema, route, content และ webhook ผ่านก่อน deploy
